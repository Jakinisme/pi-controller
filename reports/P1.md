## 1. Sign and axis conventions

DRL is the authority (`CONTRACT.md` §1, §2, §4.6; `sim/thrusters.py`):

| quantity | DRL | PI | agree? |
|---|---|---|---|
| world frame | local ENU tangent, origin = first valid GPS fix (`CONTRACT.md` §1) | same convention, `src/utils/geo.py` (equirectangular, R = 6 371 000 m) | yes |
| `psi` / heading | radians clockwise from north in DRL internals; degrees clockwise from north at the Pi boundary (`CONTRACT.md` §1, §4.6) | degrees [0,360) clockwise from north (`src/sensors/fusion.py` `FusedState.heading`) | yes |
| +surge | body x, forward along bow (`CONTRACT.md` §2) | forward (`src/control/thrust.py:43` `surge: float = 0.0  # Forward (+)`) | yes |
| +sway | body y, starboard = right (`CONTRACT.md` §1) | right (`src/control/thrust.py:44`) | yes |
| +yaw | `r = dpsi/dt`, positive = bow turns to starboard, i.e. clockwise seen from above (`CONTRACT.md` §1) | clockwise (`src/control/thrust.py:45`) | yes |
| heading error sign | `psi_err = wrap_pi(psi_goal − psi)`, positive = turn starboard (`CONTRACT.md` §1) | `src/utils/geo.py:98` `heading_error(current, desired) = (desired − current + 180) % 360 − 180`, positive = turn right | yes |
| mixer | `configs/vehicle.yaml:35-40` "verbatim from firmware" | `firmware-esp/src/header/config.h:85-90` MIX_MATRIX | identical rows |
| per-motor invert | `[false, true, false, false]` (NE reversed) | `config.h:100-105` | identical |

MIX_MATRIX, rows NW, NE, SW, SE; columns surge, sway, yaw:

```
NW { +1, +1, +1 }
NE { +1, -1, -1 }
SW { +1, -1, +1 }
SE { +1, +1, -1 }
```

What is **not** verified: the physical sense of sway and yaw on the real hull. DRL says so
itself (`sim/thrusters.py` header: "the physical sense of sway/yaw is unresolved
(INSPECTION.md H6), so the blind sign factors live in `vehicle.yaml: signs.*` and default to
identity"), and `vehicle.yaml:45-50` marks every sign TODO-bench. The command-level
convention agrees; whether the hull actually moves that way is a bench question (props-off
sign table, then per-axis motor test — see `docs/RL_INTEGRATION.md`).

Consequence for deployment: the policy's action is fed into the same `[surge, sway, yaw]`
that the PID already produces, so a sign error would be a *shared* error, not a new one.
That is exactly why the bench test is a gate and not a nicety.

## 2. Rates and decimation

- Policy step: `policy_dt_s = 0.1` s (10 Hz), from `models/policy_meta.json`; the observation
  is a 10-deep history (`k_history: 10`), so the ring buffer assumes 10 Hz.
- Control loop: `FUSION_UPDATE_RATE_HZ = 20` (`src/config.py`), same rate for
  `SensorFusion.update_loop()` and `ASVSystem.control_loop()` → 20 Hz, i.e. 50 ms ticks.
- Decimation: the mux runs `adapter.step()` only when
  `now − last_step_t >= policy_dt_s` (with a 10 % guard, `>= 0.09 s`), using an injectable
  `time.monotonic()` clock. Every in-between tick re-sends the **last applied** command and
  runs no inference. Net: one inference per two control ticks.
- Jitter: when the measured gap between policy steps deviates from `policy_dt_s` by more than
  30 %, the mux logs a rate-limited warning containing the jitter in ms, because the
  observation history silently assumes 10 Hz.
- Inference cost measured on this laptop: 1.8 ms/step through `RLAdapter`; `bench_inference.py
  --n 1000` reports p50 0.143 / p95 0.244 / max 0.465 ms for the bare session. **These are x86
  laptop numbers, not Pi 3B numbers** — the Pi number must be measured on the Pi
  (`tools/bench_inference.py`). `RL_MAX_INFERENCE_MS = 50` is therefore an unvalidated
  deployment limit, not a measured one.

## 3. Estimator keys → real sources

`RLController.step(estimator_state, goal)` per `CONTRACT.md` §4.8. Mapping actually wired:

| key | source | note |
|---|---|---|
| `lat`, `lon` | `FusedState.latitude/longitude` (GPS, low-passed in fusion) | deg |
| `heading_deg` | `FusedState.heading` (mag + gyro complementary, GPS-course corrected above 0.3 m/s) | deg CW from north |
| `yaw_rate_deg_s` | `FusedState.yaw_rate` ← `imu.data.gyro_z` | deg/s |
| `speed_mps` | `FusedState.speed` ← `gps.data.speed_over_ground` | m/s |
| `course_deg` | `gps.data.true_course` (`src/sensors/gps.py:37,169`) — **not in `FusedState`** | deg; meaningless at low speed, handled below |
| `gps_valid` | `FusedState.gps_valid` (`src/sensors/fusion.py:102,160-165`) | see gate note |
| `imu_valid` | `FusedState.imu_valid` (`fusion.py:172`) | |
| `mag_valid` | `FusedState.mag_valid` (`fusion.py:174`) | |
| `sensor_ok` | `gps_valid and imu_valid and mag_valid` | derived at the mux |
| `t` | fresh `time.monotonic()` at read time | **not** `FusedState.timestamp` |

Two things worth stating plainly:

- **Gate choice.** `FusedState.gps_valid` is the right flag: fusion sets it from
  `self.gps.has_fix and not self.gps.is_stale` (`fusion.py:102`), so it already encodes
  staleness. `gps.data.valid` alone is only "a sentence was parsed" and ignores age —
  `drl/runtime/policy.py`'s module docstring warns about exactly this legacy `has_fix` trap.
  The mux uses the fused flag.
- **Course at low speed.** COG is undefined when the vessel is nearly stationary. This is
  handled inside the policy, not by substituting heading: `RLController` passes
  `min_speed_mps = 0.3` to `common/estimator.estimate_body_velocity`, which only adopts
  `u = sog·cos(cog − heading)`, `v = sog·sin(cog − heading)` when the fix is valid **and**
  `sog >= 0.3 m/s`, and otherwise decays the previous estimate with `decay_tau_s = 1.0`
  (`CONTRACT.md` §4.10). A stale/zero course therefore decays rather than poisoning the
  observation. `course_deg` is still passed through verbatim.

- **Timestamp caveat (affects the watchdog).** `FusedState.timestamp` is set from
  `time.time()` (`fusion.py:94,175`), i.e. wall clock, not monotonic. Mixing it with a
  monotonic clock would produce nonsense ages (NTP step, suspend/resume), so the mux does
  **not** age-check the fused state against `FusedState.timestamp`. The mux keeps its own
  monotonic "when did I last get a state I could act on" stamp and fires the watchdog when
  that stamp is older than `RL_WATCHDOG_S` (0.5 s), plus the policy's own internal
  watchdog on the policy-step gap. Decision recorded in the mux source as a comment, and in
  `reports/P1_T06_mux.md`.

## 4. Navigator behaviour and the last-waypoint mismatch

`src/control/navigation.py` (`WaypointNavigator`):

- Arrival radius: `WAYPOINT_ARRIVAL_RADIUS_M = 2.0` (`src/config.py:63`), applied at
  `navigation.py:175` (`if dist < self._arrival_radius`). Same 2.0 m the policy trained with.
- Advance rule: on arrival, `current_wp_index += 1` (`navigation.py:181`), then the next
  waypoint is used immediately for the same tick's heading/speed.
- After the LAST waypoint: `navigation.py:183-184` calls `self.stop()` → `NavigationState.IDLE`
  and zero thrust. **Mismatch:** training treats the final waypoint as a *hold point*
  (`CONTRACT.md` §4.6: "mode 1 = station keeping, goal = hold point, target velocity 0,
  psi_goal = hold heading"), i.e. the vessel is expected to settle and stay. On the Pi it
  goes idle and drifts. It is not a safety bug (idle is the safe end state) but it means the
  end-of-mission behaviour seen in simulation is **not** reproduced, and the policy never
  gets a chance to show its station-keeping there.
- Goal exposure for `next`/`next2`: `nav.waypoints` is the full list and
  `nav.current_wp_index` the active index, so `waypoints[idx+1]` / `waypoints[idx+2]` are
  directly available. At the last waypoint there is no `idx+1`, so those keys are omitted
  and the policy sees them as 0.0 — a weaker signal than training had, exactly the case
  `drl/runtime/policy.py` flags as `TODO`. Same at the second-to-last waypoint for `next2`.
- `Waypoint` carries `heading_hold` (optional), which is passed through as the goal heading
  when present; otherwise the goal heading defaults to the current heading (waypoint mode) or
  to `hold_heading` (station keeping).

## 5. Firebase command replay safety

`src/comms/firebase_bridge.py`:

- `__init__` sets `self._last_command_ts = time.time()` with the comment "Ignore commands
  older than boot" (`firebase_bridge.py:107`).
- The streaming listener (added by the previous task) drops any event with
  `cmd_ts <= self._last_command_ts` (`firebase_bridge.py:247-250`).
- The polling fallback applies the identical filter (`firebase_bridge.py:292-295`).

So after a process restart the `commands/` node still sitting in the RTDB (possibly
`mode: "waypoint"`, possibly `controller: "ppo"`) has a timestamp from before boot and is
discarded; the system comes up IDLE with PID. The new optional `controller` field cannot
reintroduce the replay bug because it is parsed **inside** `RemoteCommand.from_dict`, i.e.
behind the same timestamp gate — it is never read on its own and never applied at startup.
This is asserted by a test (`tests/test_rl_restart.py`).

## 8. Pi 3B headroom (what can and cannot be claimed here)

Measured on this laptop (x86, Python 3.13.3): 1.8 ms per policy step through the adapter,
0.143 ms p50 for the bare session; that is ~2 % of a 100 ms policy period.

Not measured, and not claimed: CPU/RAM on the Pi 3B with the sensor threads, the ML
fan-out (`MLFanout`), Firebase and onnxruntime alive at once. The Pi 3B has 4 slow A53
cores and 1 GB RAM; the adapter is deliberately built with
`intra_op_num_threads=1` so inference cannot starve the sensor threads, but the actual
headroom is a measurement to be taken on the Pi (`tools/bench_inference.py` there, plus
`vmstat`/`ps` during a mock run). Until that is done, `RL_MAX_INFERENCE_MS = 50` is an
unvalidated safety threshold.

## 9. Report-only findings

1. **Sign/axis**: no disagreement at command level (§1). Physical sway/yaw sense on the hull
   is unverified (H6) and must be settled by the props-off bench test before any water trial.
2. **Rate**: policy 10 Hz vs control loop 20 Hz needs decimation, implemented; the real
   question is whether the 20 Hz loop should be reduced to 10 Hz later (halves CPU, halves
   ESP32 chatter, but also halves sensor responsiveness). Recommendation: keep 20 Hz for
   sensing and decimate the policy, which is what was built.
3. **Observation assumptions the Pi cannot fully satisfy**:
   - `u, v` come from SOG/COG because there is no body-velocity sensor (H7). Above 0.3 m/s
     this is a coarse estimate; below it, decay. The policy has never seen real GPS lag
     (~1 Hz NMEA, position low-passed at α = 0.7).
   - `heading_deg` is trusted as an absolute reference, but it carries the magnetometer
     mount offset (`HEADING_MOUNT_OFFSET_DEG = 155.0`) and the magnetic declination
     (`MAGNETIC_DECLINATION_DEG = −1.5`) as configured constants. Both are calibration
     inputs the policy simply believes.
   - The policy was never trained with the Pi's sensor latency, its ~1 Hz GPS, or a 20 Hz
     loop jitter; the jitter warning exists to make that visible in the field.
   - `FusedState.timestamp` is wall-clock (`time.time()`), not monotonic, so any age-based
     safety check must use the mux's own monotonic stamp (implemented that way).
4. **Last waypoint**: navigator goes IDLE where training expects a hold point (§4).
5. **Logger vs replay**: `runtime/infer_replay.py` can replay the log for the required
   columns, but `goal_heading_deg`, `next_lat/lon`, `next2_lat/lon` and `est_age_s` are not
   recorded, so station-keeping heading and the later-waypoint
   observations cannot be replayed from it (§ `src/rl/logger.py` docstring).
6. **Known vendored-code quirk (not fixed, DRL is read-only)**: `RLController.step` returns
   zeros *before* `_emit` on a geofence breach, so the breach bypasses the slew limit; and a
   non-finite session output surfaces as `source="zero", fault="nan"`. The mux therefore does
   its own tighter geofence, its own latch, and treats `source in {"zero","geofence"}` as a
   fault.
